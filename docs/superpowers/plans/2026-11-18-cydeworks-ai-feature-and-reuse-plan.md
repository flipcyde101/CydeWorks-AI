# CydeWorks AI Implementation Plan

> Historical planning reference. Read `docs/ROADMAP.md` for the current source checkpoint and later runner review findings. Local runtime evidence was not imported into this repository.

November 18, 2026. Proposed roadmap for the personal Windows release. The Dell browser preview is the baseline.

**Goal**

Turn the Dell preview into a daily workspace where an owner can send scoped work to a local or approved hosted model, review a real repository change or cited brief, and see exactly what ran, what data moved, and what each attempt used.

**Architecture**

Keep the current browser UI, Node 24 workspace service and SQLite task records. CydeWorks owns task identity, permissions, the execution journal, review, receipts and data controls. External engines, model servers, terminal services and factory tools connect through adapters with explicit capabilities and destinations.

**Specification**

This plan carries forward requirements R01 through R15, adds the requested small agent team and per-task provider selection, and starts from the actual Dell cutover. [Project spec](../../../outputs/Project%20Spec.md) · [Prior completion requirements](../../../outputs/BFE%20Harness%20Completion%20Plan.md#2-product-requirements). Historical Dell delivery evidence is not included here.

## What the Dell actually does today

The preview returned HTTP 200 ready during this planning pass, and its startup entry-point hash matched `harness/server.mjs`. The November 18 cutover records 280 workspace tests, 31 receipt analytics tests, 3 preview guard checks, 6 synthetic browser checks and 7 real local browser checks. A separate use of the running preview produced an accepted three-citation brief on Qwen3-4B Q4 in 5.1 seconds and an inspectable receipt. Usage also showed missing receipts for at least two older tasks. The historical delivery evidence and local task link are not included in this repository.

The live code accepts a pasted snapshot or small text file, approves one route, and returns a cited brief or single-file proposal for review and download. Terminal control currently covers observation and run actions. Repository writes, test execution inside a qualified runner, general terminal input, durable worker continuity and hosted connections are the main gaps between this preview and the personal release. The public MIT GitHub preview is a separate source snapshot and its features should be read from its own README. [Live workspace source](../../../harness/README.md) · [Public preview](https://github.com/flipcyde101/CydeWorks-AI)

## Build order and acceptance

Start the legacy-receipt repair and the runner feasibility check together. The scope and approval work can proceed during host qualification. Ship the first local repository pilot after packages 1 through 4 pass and the new worker passes the existing read-only observation, detach, reattach and Stop flows. Extend terminal input in package 5. Packages 6 and the offline portions of 7 and 8 can start during host qualification. Connect live workers or accounts after their prerequisites pass. Start package 11's offline restore and launch work early. Package 12 decides personal release readiness.

Use Node 24 and the existing test runner. Each package starts with a regression or contract fixture, implements the smallest full path through the real entry point, and reruns its tests and the complete `npm --prefix harness test` suite. Browser, real-engine and recovery gates get their own evidence. The working `harness` directory and GitHub export checkout are separate. At implementation kickoff, identify the approved source checkout and record the staged baseline before making code changes. Use reviewable commits in that checkout.

The owner has one local workspace identity for this release. Approvals are server-enforced. Source, secrets and provider credentials stay local by default. Run destructive or external actions only under the existing explicit approval rules. Add new tests in the proposed paths below, using disposable state and synthetic inputs. Preserve the approved preview fallback during staged installs.

## Review cases that can invalidate a milestone

- An older receipt missing one material fact appears beside a valid current receipt. The valid totals must remain visible with coverage disclosed. Package 1 owns this check.
- The owner approves, another view changes source or route, and a delayed request arrives. The stale request must have no dispatch or charge. Package 2 owns this check.
- A worker ends or restarts after producing a partial patch. The source checkout stays intact and the old attempt keeps its evidence and unknown-outcome hold where needed. Packages 3 through 5 own this check.
- A provider retries or reports usage after cancellation. The receipt and ledger attribute events once and retain incomplete charge coverage. Packages 6 and 7 own this check.
- A restored project has an imported handoff, expired credential reference or missing artifact. It opens in a safe draft or held state and makes any evidence gaps visible. Package 11 owns this check.
