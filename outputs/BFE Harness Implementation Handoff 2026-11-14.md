## Verified in synthetic tests

- The source brief and single-file proposal flow supports scope approval, structural checks, review and metadata export. These checks do not prove that a coding task is correct or that a repository is protected.
- An operator can edit a review-stage brief or single-file proposal, retain the original proposal, and rerun structural checks and the patch before accepting. It does not write the edited result into a repository. Uniform CRLF and CR line endings are preserved; editing mixed endings requires an explicit normalization choice. Stale versions and conflicting edits are held. Standard and minimal exports omit the original and edited proposal text.
- Uncertain provider outcomes block automatic retries. Interrupted pre-dispatch work and in-process fixture work can be retried when the saved evidence supports that conclusion. A SQLite lock prevents two compatible new services from opening the same workspace. Older incompatible services would not honor this lock.
- The desktop startup service exchanges its temporary session over private IPC. Source now uses an Electron utility-process design instead of general Electron Node mode. Simulated tests cover authentication, heartbeat expiry, stale heartbeat rejection, lock release and reopening saved records. The actual Electron utility process and Windows application have not been run.
- A minimal metadata export excludes source text, task names, filenames, identifiers and other non-allowlisted fields. The preview and download use the same generated JSON. The minimal preview was inspected in a browser with synthetic data; a physical download and comprehensive accessibility review remain unverified.
- A reviewed, explicitly confirmed task-record removal flow has been added in source and tested with synthetic data. It removes only one record from the active workspace database, holds active or unresolved attempts, and retains a pseudonymous audit. It does not remove OpenCode working files, backups or provider copies and does not promise secure erasure. Independent review and focused synthetic tests passed. The dialog and successful removal were also checked in a disposable browser workspace, including cleared form fields. No user record was removed during development.
- The Needs you list groups multiple reasons into one item per task. Progress distinguishes waiting, possible stalls, stop requests, disconnection and review. Unknown completion times remain unavailable.
- The usage view separates direct provider counts from OpenCode engine-defined counts. New OpenCode attempts can show up to 64 observed step events, including cache reads, cache writes and reasoning values when reported. Repeated IDs are deduplicated; conflicting, ambiguous or truncated step sets do not receive aggregate totals. OpenCode can normalize provider counters or report zero for missing upstream values, so these figures are not invoices. Cancellation preserves observed steps when the local process returns them; a crash can still lose an in-flight receipt. No cost or router savings claim is established.
- Local Ollama inventory can show additional installed model names, but only the existing preview allowlist can be selected for execution. A readiness check holds reported remote entries, unknown or enabled cloud status, unavailable model digests, oversized models and insufficient system memory. The digest is reported and checked before dispatch, but Ollama still receives a mutable tag, so it does not prove which model executed. Passing the check does not qualify model quality, guarantee GPU offload or establish an isolated network boundary. This is not full model independence yet.
- The isolated swarm coordinator validates dependency graphs, lexical ownership conflicts, approval expiry and restart handling. It has no real worker, user interface or filesystem enforcement attached. It must not dispatch repository-writing agents until a separately qualified broker enforces scope and verifies artifacts.
- The isolated accounting ledger handles cumulative receipt replays, unknown usage, independent attempts, budget reservations, concurrent claims and unsettled cancellations. It is not connected to a provider, the production task database, a router or paid work. Provider-evidence authentication, correction workflows and integrated caps remain to be built.

## Live evidence and limits

Earlier direct Ollama trials with `qwen3:1.7b-dell-cpu` returned the unchanged file for the requested replacement. On 2026-11-15, the full CydeWorks API to OpenCode to local llama.cpp path ran synthetic tasks in a disposable in-memory workspace. A function-edit task returned unchanged code and failed its expected-text check. A simpler greeting edit passed the checks, syntax validation and a behavior assertion, and was accepted in the test workspace. Take, status, detach, reattach and release succeeded through the terminal API while the model was running. The code remains a proposal for review, not a general repository-writing agent.

After owner approval, the existing Ollama Inc. signed `llama-server.exe` was started with `Qwen3-4B-Q4_K_M.gguf`, alias `qwen3-4b-local`, 4,096 context and one server slot. It was healthy and listening only on `127.0.0.1:8080` at the latest check. Its command includes `--offline`; this is not proof of operating-system network isolation. Windows listed the server as a GPU user, but its per-process GPU memory and exact offload percentage were unavailable. At one checkpoint the machine had approximately 235 MiB of free VRAM and 11.7 GiB of available system RAM. These values and process lifetime can change.

Three live synthetic attempts used the same small greeting edit through CydeWorks, OpenCode and that server. Each produced a proposal that passed the selected text, JavaScript syntax and behavior checks. The operator-edit API preserved the original, updated the patch and allowed review acceptance, and a single observed OpenCode step receipt was captured. In the latter two runs, confirmed takeover, rejection of a stale lease, detach, observation of the same still-running attempt without control, retake and release succeeded after OpenCode started. The first run performed its terminal controls before OpenCode started and is not evidence for live detach. All attempts used disposable in-memory workspaces, not the owner's saved tasks or a real repository. Repeating one easy task does not qualify general coding quality, and a live multi-step receipt remains unverified.

A headless browser check used the active source in a separate in-memory workspace and confirmed that the OpenCode to llama.cpp route was selectable, its destination details appeared, and the approval checkbox worked. It did not unlock or alter the owner's saved workspace. The live preview itself passed its asset and record-preservation checks.

Earlier read-only inspection showed that the then-running Ollama service reported cloud features enabled. Ollama was not running at the latest check. The preview holds Ollama routes until the service reports cloud features disabled. Earlier inventory for the four preview names did not report remote metadata; that is not proof of an offline boundary. A qualified network boundary is still needed before relying on a local-only claim. No Ollama setting was changed.

The owner approved one temporary cloud-disabled Ollama instance and a disposable local key pair. Inspection of Ollama 0.40.16 showed startup can modify or prune its model directory even when ordinary pruning is disabled, so the test used an empty project-local model store instead of the owner's model directory. The test process started and reported a loopback listener, but its status endpoint timed out twice. The parent process was stopped, both approved temporary key files were removed, and the original Ollama service remained responsive with its settings unchanged. No model was loaded or prompted. A supported elevated process check found only the pre-existing Ollama and llama processes, all started before this test. The timeout cause is not established, and the file-free test scratch tree is retained. A repeat would require a fresh approval for a new temporary key pair.

The present terminal surface exposes observation, ownership, status, detach and stop controls. It is not a general interactive shell, does not yet implement human input to a PTY, and has not established that stopping OpenCode also stops Ollama. Provider outcome uncertainty remains a recovery hold.

On 2026-11-15 the owner approved bounded WSL capability checks. Ubuntu 24.04 started with UID 0 by default; `nobody` could create separate user, PID, mount and network namespaces. A synthetic process in the new network namespace could not reach a parent loopback listener that a control connection reached. A private temporary mount hid a synthetic marker only inside that namespace and left the parent marker intact. A separate test also showed that unshare without filesystem confinement could read an out-of-scope synthetic file. A more restrictive disposable prototype failed twice with exit code 32 while binding `/usr`; the cause was not classified, and the experiment stopped. The prototype did not reach its scoped-file, gateway or process checks. Windows drives and WSL interop were present by default, `bwrap` was unavailable, and Node was not found in the distribution. These results show partial feasibility, not a qualified runner. Interop escape, scoped files, model-gateway access, credentials, child processes, resource limits, protected checks and verified process-tree termination still require testing. Docker's daemon was unavailable during this check. No OS setting was changed.

The Electron development dependency is present locally, but its downloaded executable is unsigned. No native window, approved signing identity, packaged artifact, fuse configuration, OS execution acceptance or cross-platform build has been verified. The current source still needs a complete packaging and signing workflow. Electron recommends utility processes when disabling the general Node mode, plus ASAR integrity and the only-load-from-ASAR fuse for Windows and macOS: https://www.electronjs.org/docs/latest/tutorial/fuses and https://www.electronjs.org/docs/latest/tutorial/asar-integrity.
