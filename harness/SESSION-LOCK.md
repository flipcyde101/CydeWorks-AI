# Workspace session lock

Backend and UI contract, 2026-11-18. Lock and the inactivity deadline end the single in-memory operator session. They do not restart the existing preview.

## Request and response

Send authenticated, same-origin `POST /api/session/lock` with `Content-Type: application/json` and exactly `{}`. Unknown fields return 400, other methods return 405, missing/expired sessions return 401, and origin violations return 403. The existing request-size limit applies.

Successful response:

```json
{"locked":true,"scope":"all-workspace-views","terminalControlReleased":true,"stopsWork":false,"requiresAccessFile":true}
```

The server replaces its in-memory session value and expires the calling browser's session cookie. Every existing view's old cookie is rejected, even if a view keeps that cookie locally. The workspace access file is unchanged. A new POST to `/api/session` using that file is required to unlock. A repeated Lock using the revoked cookie returns 401 and does not renew access.

## Inactivity

The workspace session ends 15 minutes after the last operator action. The deadline starts when the in-memory session secret is created, including a desktop bootstrap that creates the secret without `POST /api/session`. The server samples a monotonic clock and a wall clock and remembers the last finite sample. If either sample is not finite or moves backward, the session ends instead of lasting longer. It also ends when either clock is at least 15 minutes ahead of the last operator action. The deadline moves on a successful unlock and on an authenticated POST, except a terminal heartbeat, a terminal detach, and `POST /api/cost-presentation`. Those three are lease renewal, view teardown, or automatic presentation. Authenticated GETs do not move the deadline. That includes task lists, task reads, attention, route inventory, and other reads. A terminal heartbeat renews only the 15-second terminal control lease. Terminal release, status, take, stop, task changes, and handoff review still move the workspace deadline.

At the deadline the server replaces the session secret, revokes terminal control, and expires a cookie that still matches the old secret. It does not stop approved work. The 15-second terminal lease is unchanged. Unlocking after the deadline still requires the access file. The session id is not put in a URL. Unlock issues the same secret as two cookies, Path `/api` and Path `/api/`. Those paths are different cookies. A deletion for Path `/api` does not remove Path `/api/`. The server accepts a request when any presented `bfe_session` value matches the current secret. After the secret changes, a value saved from the previous Path `/api/` cookie no longer matches. Expiry still deletes only Path `/api`. The cookies stay HttpOnly and SameSite Strict. The current HTTP preview does not add Secure. The desktop bootstrap still sets only Path `/api`, and that single cookie remains accepted.

The cookie is not enough for a browser view. A request that sends `Sec-Fetch-Site`, including `none` on a direct top-level navigation, and any request that sends `X-Workspace-View`, must also send the 32-hex view id returned by that view's own `POST /api/session`. Unlock returns `{authorized:true, viewId, viewGeneration}` and sets `X-View-Generation`. Lock and the idle deadline rotate the generation and forget every admitted view id. A stale view receives 401 and does not rotate the session or expire the cookie. A caller that omits both `Sec-Fetch-Site` and `X-Workspace-View` stays on the cookie check. That keeps non-browser clients working. A real browser fetch from the page sends `Sec-Fetch-Site`, so another tab cannot omit the header and reuse the new cookie. The desktop window still denies node integration and keeps context isolation, the sandbox, and web security. It still cancels navigation and requests that leave the service origin. Its bootstrap cookie stays Path `/api`, so the document request for `/` does not send that cookie. The view id is not put in a URL, a cookie, or the ready message. The launcher proof is not put in a URL, a cookie, local storage, session storage, a log line, the ready message, or the bind acknowledgement. While desktop bootstrap is on, the server keeps one unissued view id. After the ready message, the launcher binds one 64-hex proof over the utility parent channel. A later bind of that same proof is accepted. A different proof does not replace it. `POST /api/desktop-view` admits the view only when the current launcher cookie and that bound proof are both presented, and only once. The page does not call that route. The intended main frame calls `claimDocument` on the preload bridge. The bridge carries no secret. The launcher accepts the call only when the IPC sender is that window's main frame and the frame origin is the service origin. The main process then performs the one claim request. A cookie without the proof is rejected and does not take the ticket. A wrong proof does not take it. Fetch Metadata does not issue or consume the view. A document navigation of `/`, including one that forges `Sec-Fetch-Site` `none` or `same-origin`, returns the ordinary page and leaves the view unissued. A second claim receives no view id. The same webContents may retry until the proof is cleared, including a reload before a successful claim. After success the proof is cleared, so a replay or a reload claim is not admitted again. The stored view id in that document's session storage is the existing per-view admission, and a reload with no opener keeps it. If Lock or the idle deadline rotates the generation before a claim is admitted, that claim does not receive the view id and the server does not mint another. A claim whose body is still open when Lock replaces the session is rejected and does not take the ticket. The idle claim spends the ticket. A caller that omits both `Sec-Fetch-Site` and `X-Workspace-View` stays on the cookie check for other routes. A protected GET that sends `Sec-Fetch-Site: none` still requires the admitted view id. Direct navigation of GET `/` is not a protected route and does not admit a view. A new service process does not accept the previous process's proof and requires its own bind. This candidate stays disconnected from integration. If the invoking frame is missing, the claim returns no view id. An empty document then follows the existing boot path and conceals the workspace instead of opening it. That is not a successful first open.

The utility parent channel is trusted to bind the proof. A process that can post a message to the worker can bind it. The one claim request is loopback HTTP from the main process, so a local observer of that connection can see the cookie and the proof on that one request. Replay after delivery fails. Electron 45 identifies the invoking frame with `senderFrame` and `webContents.mainFrame`. That is the supported facility used here. This change did not execute Electron, so that frame identity is not a live observation. The page stores the admitted view id in its own session storage through the existing admit path. The proof is not stored there.

A same-origin window that starts with an opener can receive a copy of the first document's session storage and the shared cookie. That window drops the copied view id and generation before it may open. It does not keep the first document's admission, and it does not receive the desktop claim while it must stay concealed. A reload has no opener and keeps its own stored view. The copied local lock stays in place.

Each Lock writes a distinct shared value, `lock.` plus 32 hex. That includes a view that is already concealed and a repeated Lock. A continuation reads that shared value synchronously before it submits the access file and again before it admits the response. It stops when the value changed. It does not wait for the storage callback, and it does not replace the newer revision. The literal value `locked` still conceals a view that already stored it. A repeated read of the same revision does not move the epoch.

A Lock request for a session that has already reached the deadline returns 401. The access file is unchanged. An authenticated POST body that is still arriving when the deadline passes is rejected by the same recheck used for Lock. An authenticated POST whose body is later rejected still moves the deadline, because the deadline moves after that recheck and before the route's own validation. A terminal heartbeat, a terminal detach, and `POST /api/cost-presentation` do not. A models probe that is still running when the deadline passes, and that finishes only after a newer unlock, returns 401 and does not send a cookie deletion. That case is delayed server computation. A deletion header that was already complete before the newer unlock can still arrive afterward. It removes the new Path `/api` cookie and leaves the Path `/api/` cookie, which carries the new secret. The unlock cookie stays in effect. A response whose presented cookie still matches the secret being ended still expires that cookie.

## Running work and request races

Lock releases any active terminal lease without closing its control channel, cancelling the task or stopping a worker. Already-approved work may finish while locked. Freshly unlocked observers must explicitly Take control again. A lease held before Lock is invalid even after unlocking.

Authenticated POST requests recheck their session after the complete body is received and before dispatching a mutation or returning a processing result. A body that was still arriving when Lock occurred cannot mutate a task afterward. An unlock request already in flight before Lock returns 409 if it finishes afterward; it must be consciously retried with the access file. Slow inventory/readiness probes recheck authentication before returning their results.

Lock cannot undo a mutation already committed or work already approved. A lost response can still have an unknown outcome. Keep pending submission identifiers for reconciliation and never treat a lock or 401 as proof that an earlier run did not start. Lock is distinct from Stop, Detach and task removal. Approved work keeps running.

## Frontend obligations

- Explain that Lock affects every view while approved work continues.
- Discard local terminal lease tokens, disable mutation/download controls and conceal sensitive task content when locking or receiving 401.
- Preserve only the minimum pending request identifiers needed for recovery. Do not store source or session secrets for convenience.
- After a lost Lock response, locally lock the view and use a read-only authenticated check if needed. Do not silently unlock or resubmit earlier commands. Legacy writes that unconfirmed promise to session storage before the request. Reload and ordinary navigation back to `/` keep the view on the access file and do not treat the reload as server confirmation. The confirmed sentence is shown again only when that outcome was already stored. Other tabs hear the change from `localStorage` key `bfe-shared-generation` (`storage`, plus `pageshow` and `visibilitychange`). A change of that value to `locked`, to a new `lock.` revision, or to a generation this tab did not publish, moves the unlock epoch even when the view is already concealed. The access-file read and the unlock response each compare the shared revision before they continue, so they stop before the storage callback runs and do not replace a newer revision. The tab that wrote the value records it before the next visibility check. A visibility check that sees the same value does not move the epoch. Polling and a later 401 are backstops. BroadcastChannel is not the signal. A tab does not receive another tab's view id.
- Unlock using the existing access-file flow, reconcile saved state, and reattach read-only.

This is authorization revocation. It does not erase already-rendered text, clipboard contents, downloaded files, browser memory, task records, worker artifacts or provider data. Legacy and experience both offer Lock. Legacy posts exactly `{}` and shows "Workspace session terminated in every view. Approved work keeps running, and terminal control was released. Unlock with the access file." only after the server returns `locked: true`. A lost response is an unconfirmed local lock. A 401 means the session had already ended. Any other success body is unconfirmed. Experience uses the same confirmation rule and the same termination sentence, and it still ignores that result when a newer unlock or Lock owns the screen. Legacy keeps a session epoch. Lock conceals the view before the response: the workspace is hidden and inert, every open dialog is closed and inert, polls stop, the terminal lease is dropped, and task actions stay disabled. An export dialog outside the workspace is included. Closing it drops its cached export, and a download that still holds that text is refused while the view is locked. Already rendered text stays in place. A file read, a terminal Take, and an approved Run that succeed after Lock do not write those results or start polling. The same per-request epoch covers release, status, stop, detach, route refresh, form submit, proposal save, draft copy, removal, and export load. Each Lock request keeps the epoch returned for that request. A later Lock cannot make the earlier response current. That concealment remains when the lock request fails. A task or list read that was already in flight cannot mark the view connected or rebuild an actionable list afterward. A lock response that arrives after a newer unlock does not lock the view again or replace the unlock status. The Lock control stays hidden until this view has opened the workspace, and confirming Lock moves focus to the access file when that control is visible. If opening the workspace fails after the access panel was hidden, the view shows the access file again, hides and inerts the workspace, stops polls, and moves the epoch so the failed open cannot write. A failure before that panel is hidden still conceals the workspace and leaves the access panel visible. A remembered task that is missing does not use the failed-open recovery. Neither view erases already rendered text. Reading the workspace does not keep the session open. Restart, Lock, and 15 minutes without an operator action end it. No desktop-bootstrap session is automatically reissued after Lock or after the idle deadline; the current app view must use the normal unlock flow. One access-file selection covers the read, the unlock POST, and the response. A newer selection or Lock drops that attempt before the POST and again before the view is admitted. A response that arrives after that drop is not admitted. If the server had already accepted that request, the unused view id stays unstored until the next Lock or idle rotation, and this view does not open. Cancel and the draft-copy success notice publish only while their own epoch is still current. An allowed export records a count of one and does not keep the export text. A failed open after the access panel was hidden also drops this view's admission.
